# 网页聚类与主题跟踪可实现技术方案

## 1. 目标与范围

### 1.1 目标

面向“把搜下来的网页进行聚类，将聚类结果显示给用户，用户可以选择其中一个类标为关注，并持续跟踪该主题”的业务目标，建设一套可在当前项目中分阶段落地的实现方案。系统应支持：

1. 从网页或 RSS 来源采集文章。
2. 对网页正文进行清洗、分词和标准化。
3. 使用 TF-IDF 将文本表示为可聚类的数值向量。
4. 自动估计较合适的聚类数 K，并执行聚类。
5. 为每个簇提取关键词、代表文章和可读主题名。
6. 允许用户选择某个簇作为“关注主题”。
7. 对后续新网页进行主题相关性匹配，输出持续跟踪结果和情感变化。

### 1.2 非目标

当前阶段不追求：

1. 跨语言统一主题建模。
2. 基于大模型的开放式主题命名。
3. 海量数据下的分布式在线聚类。
4. 高精度舆情情感分类模型训练。

本方案优先保证课程项目、演示系统和中小规模原型的可实现性与可解释性。

## 2. 当前项目现状与改造方向

当前 `web classification` 项目已经具备以下基础能力：

1. 数据抓取与演示数据切换。
2. 基于 `TfidfVectorizer` 的文本向量化。
3. 前端主题簇展示、主题跟踪和情感趋势展示。
4. 简化版 KMeans 与聚类结果可视化。

但当前实现更接近“预定义主题 + 规则归类”，还不是真正意义上的“先聚类，再由用户选择主题跟踪”。因此需要完成以下改造：

1. 将主题归类入口从固定主题词典切换为真实聚类结果。
2. 增加中文正文抽取、分词、停用词和同义词归一流程。
3. 增加 K 自动选择与聚类质量评估。
4. 将“用户关注主题”从页面状态升级为可持久化的主题对象。
5. 将后续网页筛选逻辑从“同类文章过滤”升级为“基于主题表示的相关性匹配”。

## 3. 总体架构

建议采用如下处理链路：

```text
数据采集 -> 正文抽取 -> 文本清洗 -> 中文分词/标准化 -> TF-IDF 向量化
       -> K 值选择 -> 聚类 -> 关键词提取/主题命名 -> 用户选择关注主题
       -> 新网页增量匹配 -> 情感分析 -> 可视化展示
```

### 3.1 推荐模块拆分

建议在当前 `src` 下按职责拆分：

1. `live_fetch.py`
   - 负责 RSS/网页列表抓取。
2. `content_extract.py`
   - 负责 HTML 去标签、正文抽取、广告和导航噪声清洗。
3. `text_preprocess.py`
   - 负责中文分词、停用词过滤、词性筛选、同义词归一、数字规范化。
4. `vectorize.py`
   - 负责 TF-IDF 训练和向量转换。
5. `cluster.py`
   - 负责 K 值评估、KMeans/KMedoids 执行、聚类指标计算。
6. `topic_builder.py`
   - 负责簇关键词提取、代表文章选择、主题名生成。
7. `tracking.py`
   - 负责用户关注主题持久化、增量文章匹配和主题走势更新。
8. `pipeline.py`
   - 负责组织上述模块，组装最终返回给前端的状态。

这样做的目标是把“规则主题”和“真实聚类”分离，避免后续逻辑都挤在一个文件里。

## 4. 数据获取与预处理方案

## 4.1 输入数据结构

每篇文章至少保留以下字段：

1. `id`
2. `url`
3. `source`
4. `published_at`
5. `title`
6. `raw_html` 或 `summary`
7. `content_text`
8. `clean_text`
9. `tokens`

如果来源只有 RSS 摘要，第一阶段可以先用 `title + summary` 作为近似正文；如果抓到详情页 HTML，则优先使用正文抽取结果。

### 4.2 正文抽取

第一阶段采用“当前依赖可实现”的方案：

1. 删除 `script`、`style`、`noscript`、`iframe`、`svg` 等标签内容。
2. 删除导航、版权、评论、广告等高频噪声块。
3. 保留段落、标题、列表文本。
4. 将连续空白折叠为单个空格或换行。

实现上可先使用标准库 `html.parser` + 正则清洗。如果后续允许新增依赖，可升级为：

1. `BeautifulSoup` 做 DOM 清洗。
2. `readability-lxml` 做正文抽取。

### 4.3 文本清洗规则

对抽取出的正文执行以下规则：

1. 中文、英文统一保留。
2. 英文转小写。
3. 去除无意义符号、超长空白和重复标点。
4. 不直接删除全部数字，而是做数字规范化。

数字处理建议：

1. 保留可能构成主题信号的模式，如 `5G`、`A股`、`3nm`、`Q1`、`GPT-4`。
2. 纯日期、纯金额、纯编号可替换为占位符，如 `<DATE>`、`<NUM>`。
3. 对网页追踪参数、版权年份等低价值数字直接删除。

### 4.4 中文分词与标准化

中文分词建议使用 `jieba`，并配置：

1. 自定义词典。
2. 行业词典。
3. 停用词表。
4. 同义词映射表。

建议保留：

1. 名词
2. 动词
3. 关键英文术语
4. 领域缩写词

建议过滤：

1. 语气词
2. 过泛动词
3. 资讯模板词，如“记者”“报道”“表示”“消息称”
4. 页面噪声词，如“点击”“更多”“返回”“登录”

说明：

1. 中文不建议做英文意义上的词干化。
2. 更有效的替代方式是“同义词归一”和“词形统一”。
3. 例如将“新能源车”“电动车”“电动汽车”统一到同一个标准词。

### 4.5 预处理输出

建议为每篇文章生成三份文本：

1. `display_text`
   - 给前端显示的清洗正文摘要。
2. `vector_text`
   - 用于向量化的分词结果，如空格分隔后的 token 串。
3. `keyword_text`
   - 用于关键词高亮和主题解释的标准化 token 列表。

## 5. 特征工程方案

### 5.1 向量化方法

采用 `scikit-learn` 的 `TfidfVectorizer`，但不直接依赖其默认分词，而是将我们自己分好的词传进去。

推荐实现方式：

1. 先在预处理阶段完成分词。
2. 将 token 用空格拼接为字符串。
3. `TfidfVectorizer` 直接读取该字符串。

### 5.2 参数建议

第一版参数建议：

```python
TfidfVectorizer(
    max_features=1000,
    ngram_range=(1, 2),
    min_df=2,
    max_df=0.8,
    sublinear_tf=True
)
```

说明：

1. `max_features=1000`
   - 满足课程项目展示需求，特征数可控。
2. `ngram_range=(1, 2)`
   - 同时保留单词和词组，便于形成“物流 延误”“产品 质量”这类主题短语。
3. 中文停用词不要写成 `stop_words='chinese'`。
   - 应由预处理阶段完成停用词过滤，或传入自定义停用词列表。
4. 稀疏矩阵建议保留，不必一开始就转成稠密矩阵。

### 5.3 特征质量增强

建议额外引入以下增强项：

1. 自定义业务词典提升分词质量。
2. 对英文缩写保留原词，如 `AI`、`GPU`、`EV`。
3. 对高频但低区分度的新闻模板词额外过滤。
4. 对网站名、栏目名、作者名做黑名单清理，减少来源偏置。

## 6. 聚类方案

### 6.1 算法选择原则

建议采用双策略：

1. 默认使用 `KMeans`
   - 适合中等规模、低到中等噪声、稀疏 TF-IDF 向量。
   - 速度快，适合交互式聚类。
2. 在小规模高噪声场景下可选 `KMedoids`
   - 更稳健，可使用真实样本作为代表点。
   - 代价更高，适合文章数较少时启用。

第一版建议先落地 `KMeans`，再保留 `KMedoids` 为可选增强项。

### 6.2 K 值选择

不要写死 `K=5~8`，建议按数据规模动态生成候选范围：

1. 最小值 `K=2`
2. 最大值 `K=min(10, floor(sqrt(N)))`
3. 若用户给定业务期望，可在该区间内优先试 `5~8`

对每个候选 K 计算：

1. SSE
2. 轮廓系数
3. 平均簇大小
4. 最小簇大小

选择策略建议：

1. 先用肘部法缩小候选范围。
2. 再用轮廓系数选最优值。
3. 若多个 K 接近，则优先选择主题解释性更好的那个。

解释性判断标准：

1. 每个簇有明显关键词。
2. 极小簇数量少。
3. 代表文章主题一致性较高。

### 6.3 聚类结果输出

每个簇建议输出：

1. `cluster_id`
2. `size`
3. `keywords`
4. `raw_keywords`
5. `topic_name`
6. `representative_article`
7. `top_articles`
8. `centroid_vector`
9. `quality_score`

## 7. 聚类后处理与主题提取

### 7.1 关键词提取

每个簇取该簇内部 TF-IDF 向量均值，按权重排序选 Top N 词。

建议参数：

1. 展示给用户：Top 5
2. 系统内部保留：Top 10

需增加两条过滤规则：

1. 去掉过短词和低语义词。
2. 避免同义词重复展示。

### 7.2 代表文章选择

代表文章建议不直接取最新文章，而取“距离簇中心最近的文章”。这样更能代表该簇核心语义。

可输出两类代表样本：

1. `representative_article`
   - 最接近中心的文章。
2. `latest_article`
   - 该簇中最新的文章。

### 7.3 自动主题命名

主题命名采用“规则模板 + 关键词兜底”的方式，避免空泛标题。

推荐流程：

1. 取 Top 3 关键词。
2. 优先匹配主题命名规则表。
3. 匹配不到时，使用 `关键词1 + 关键词2` 形式生成主题名。

示例：

1. `物流 + 延误 + 配送` -> `物流问题`
2. `质量 + 退货 + 投诉` -> `产品质量反馈`
3. `价格 + 降价 + 促销` -> `价格波动`
4. 兜底命名：`电池 / 充电`

命名规则表建议独立维护为配置文件，便于后续扩展。

## 8. 用户关注主题与持续跟踪方案

### 8.1 核心原则

用户选中一个簇之后，不应在每次刷新时丢失这个主题。系统应把它固化为一个“主题对象”，而不是仅保存一个瞬时 `cluster_id`。

### 8.2 主题对象结构

建议持久化如下字段：

1. `topic_id`
2. `name`
3. `source_cluster_id`
4. `created_at`
5. `keywords`
6. `centroid_vector`
7. `representative_article_id`
8. `matching_threshold`
9. `tracked_article_ids`
10. `status`

### 8.3 新网页匹配方法

当新网页进入系统时：

1. 使用同一份词典和向量器完成预处理。
2. 将新网页转换为 TF-IDF 向量。
3. 计算其与已关注主题中心向量的余弦相似度。
4. 结合关键词重叠度形成最终得分。

推荐得分公式：

```text
final_score = 0.8 * cosine_similarity + 0.2 * keyword_overlap
```

匹配策略：

1. `final_score >= threshold` 时纳入该主题跟踪结果。
2. 若同时匹配多个主题，则选得分最高者，或允许多主题归属。

### 8.4 增量更新与主题漂移

系统不应每来一篇文章就重跑全量聚类。建议：

1. 日常跟踪使用“固定主题对象 + 增量匹配”。
2. 定期全量重聚类作为“主题重整”任务，例如每天一次。
3. 当全量重聚类发生时，用中心向量相似度把旧主题映射到新簇，减少用户关注主题漂移。

## 9. 情感分析方案

第一版仍可保留轻量词典法，但要把它明确定位为“辅助观察指标”，而不是主判定逻辑。

每篇文章输出：

1. `positive`
2. `neutral`
3. `negative`
4. `score`

按主题聚合后输出：

1. 情感分布
2. 时间趋势
3. 代表负面文章
4. 代表正面文章

2. 用户点击“关注该主题”。

## 11. 面向当前项目的分阶段实施计划

### 第一阶段：替换规则主题为真实聚类

目标：

1. 去掉 `TOPIC_DEFINITIONS` 主导的归类逻辑。
2. 由真实聚类结果直接生成簇。
3. 保持现有前端展示不崩。

产出：

1. 聚类簇来自 KMeans 结果。
2. 关键词、代表文章、簇大小可正常展示。

### 第二阶段：加入中文预处理链路

目标：

1. 增加网页正文抽取。
2. 增加 `jieba` 分词和停用词过滤。
3. 加入同义词归一和数字规范化。

产出：

1. 中文文本聚类质量明显提升。
2. 关键词拆分错误减少。

### 第三阶段：加入 K 自动选择

目标：

1. 对候选 K 执行 SSE 和轮廓系数评估。
2. 选择最优 K 并返回给前端。

产出：

1. 看板可展示 `best_k`、SSE 曲线和轮廓系数。

### 第四阶段：实现关注主题持久化

目标：

1. 把用户关注主题从瞬时簇变成持久主题对象。
2. 新网页按主题中心向量做匹配。

产出：

1. 用户关注主题不再因重新聚类直接丢失。
2. 后续文章跟踪逻辑更稳定。

### 第五阶段：优化解释性与可视化

目标：

1. 增加代表文章、最新文章、主题摘要。
2. 增加主题热度与情感变化展示。

产出：

1. 更适合课堂答辩与用户演示。

## 12. 验收标准

系统达到以下条件时，可视为满足需求：

1. 输入一批网页后，系统能生成 2 个以上语义可解释的聚类簇。
2. 每个簇能输出可读关键词和代表文章。
3. 用户能选择某个簇并创建关注主题。
4. 新网页进入后，系统能将相关文章归入已关注主题。
5. 主题页能展示文章列表、关键词和情感趋势。
6. 同一主题在短周期内不会因刷新而完全漂移。

## 13. 主要风险与应对

### 13.1 正文抽取不稳定

风险：

不同网站 DOM 结构差异大，可能导致清洗后仍含大量噪声。

应对：

1. 第一阶段优先支持 RSS 摘要和已知站点。
2. 建立站点级清洗规则表。
3. 后续再引入更成熟的正文抽取依赖。

### 13.2 中文分词效果不稳定

风险：

行业词、品牌词、缩写词容易被拆错。

应对：

1. 加自定义词典。
2. 增加同义词归一规则。
3. 对高频错误词做人工修订。

### 13.3 聚类数不稳定

风险：

数据量变化时，K 值和主题边界容易变化。

应对：

1. 采用动态 K 候选范围。
2. 聚类结果用于“主题发现”。
3. 用户关注对象使用持久主题对象，而不是直接依赖瞬时簇编号。

### 13.4 情感分析误差较大

风险：

词典法对复杂语义判断有限。

应对：

1. 将情感分析降级为辅助指标。
2. 后续可替换为中文情感模型。

## 14. 推荐的首版实现选择

为了尽快落地，首版建议采用以下取舍：

1. 数据来源：RSS + 标题 + 摘要 + 可选详情页正文。
2. 正文抽取：先用轻量规则。
3. 中文预处理：`jieba + 停用词 + 同义词归一`。
4. 向量化：`TF-IDF`。
5. 聚类：`KMeans`。
6. K 选择：`SSE + 轮廓系数`。
7. 主题命名：规则模板 + 关键词兜底。
8. 跟踪：簇中心余弦相似度 + 关键词重叠。
9. 情感：保留词典法。

这套首版方案的优点是：

1. 与当前项目技术栈兼容。
2. 可解释性强。
3. 实现成本低。
4. 足够支撑课程作业、答辩展示和中小规模原型验证。

## 15. 结论

这不是一套“理论上可行”的泛化方案，而是一套能直接映射到当前 `web classification` 项目的实施方案。它保留了当前项目现有的可视化和主题跟踪骨架，同时把核心逻辑从“预定义主题归类”升级为“真实聚类发现 + 用户选择关注 + 增量主题跟踪”。

如果按上述五个阶段推进，系统可以先在较低风险下完成真实聚类替换，再逐步补强中文预处理、K 自动选择和主题持久化，最终达到“用户先发现主题，再持续跟踪主题”的目标。
